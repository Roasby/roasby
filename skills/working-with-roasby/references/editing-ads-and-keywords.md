# Editing ads and keywords

## Ad text

To change the text of existing responsive search ads in place (Google Ads or Microsoft Ads; ChatGPT Ads ads are refused as `kind_not_supported`), read each ad's `responsive_search_ad` in `list_ad_entities` (entity_type ad: its headlines and descriptions with `pinned_position`, `path1`, `path2`, `final_url`, and `editable`). Then call `preview_update_ads` either with `ads`, each with its `ad_id` and only the parts that change (`headlines` or `descriptions` replace that whole list with their pins, so send every one, also those that stay; `path1` or `path2`, null takes one away; `final_url`), or with a find and replace: `find` (literal text, never a pattern), `replace` (an empty string takes it away), and its scope: `ad_account_id`, or `campaign_id`, `ad_group_id` or `ad_ids` (these need no `ad_account_id`), `fields` (headlines and descriptions by default; also `paths` and `final_url`) and `match_case` (true by default). Ads without a match are left out, and so is an edit that changes nothing. What the edit changes passes the same rules as a new ad (none may be left empty, `empty_ad_text`; keyword insertion such as `{KeyWord:Trail shoes}` counts by its default text), and what it leaves as it is is not checked again; a find and replace with more matches than one batch takes is refused (`batch_items`): narrow it; an ad that breaks one is refused on its own with `detail` and `ad_text.after` (the text it would have had), the others go ahead. Only responsive search ads whose text a sync read can be edited (`ad_type_not_editable`, `ad_text_not_synced`). Show the user each ad's parts before and after (`ad_text.changes`) and every refused ad, then call `update_ads` with the same arguments and the token. Each ad keeps its status, ID and history; the ad platform reviews the new text again, so it may show as under review until approved. One edit at a time runs per ad. An ad changed in the ad platform since the last sync is not sent (its item fails and Roasby syncs): preview again afterwards. Reverting the batch, or one ad of it, writes the old text back (`changed_since` when the text changed again); an AI assistant may revert ad text too.

## Keywords

To change the text, match type or own final URL of existing keywords (Google Ads or Microsoft Ads; ChatGPT Ads has none, `kind_not_supported`), read them in `list_ad_entities` (entity_type keyword: `match_type`, `final_url`, and `editable`). Call `preview_update_keywords` with `keywords`, each with its `keyword_id` and only what changes: `text`, `match_type`, `final_url` (null or an empty string takes the keyword's own one away, so its ads' final URLs are used). A final URL, and a match type on Microsoft Ads, change in place: the keyword keeps its status, ID and history. A new text, and a new match type on Google Ads (both are fixed there), replace the keyword: the new keyword is added to the same ad group paused, with the old one's own bid and final URL unless the change sets a final URL, and the old one is paused, never removed. Say plainly before the user confirms that a replaced keyword shows no ads until they enable the new one, and that the new one starts without the old one's history (no Quality Score data yet). Letter case and spacing alone change nothing. `keyword_exists` means the ad group already has that text and match type (its ID is in `detail`): Roasby never takes it as the changed keyword, so offer to enable that one instead. Other refusals: `keyword_not_synced` (sync first), `blocked_by_negative_keyword`, `duplicate_in_request`, the keyword text rules, `invalid_final_url`, `above_max_bid` (the copied bid is above a max bid lowered since). Show each keyword before and after (`keyword_change`, `replace: true` for a replace) and every refused one, then call `update_keywords` with the same arguments and the token. Once the batch is applied, follow `keyword_next_step`: `list_ad_changes` with its `batch_id` gives each new keyword as `replacement_id`, and `preview_enable_entities` with those IDs enables them after one more confirmation. Reverting the batch, or one keyword with `preview_revert_ad_change`, sets an in-place change back, or pauses the new keyword and gives the old one its status before (only the old one's status when the new keyword was removed already; `changed_since` when either changed again). Name each keyword once per call (a second item on the same keyword is refused `duplicate_in_request`: change it again once the batch is applied); while a replace or its revert is still pending, status, bid and keyword changes of both its keywords are `change_pending` too.

## Meta ads

A Meta Ads single image or video ad changes with `preview_update_meta_ad` and then `update_meta_ad` with the same arguments and the token: its `ad_id` and only the fields that change (`primary_text`, `headline`, `description`, `link`, `call_to_action`, `url_tags` for URL parameters such as utm tags; null clears `description` or `url_tags`). Read the ad's current text in `list_ad_entities` first. Tell the user that the ad gets a new creative with everything else as it is and that Meta reviews it again before it runs with the new text. Refusals: ad_text_not_synced (sync first), meta_ad_not_editable (a Page post, carousel or ad with several texts: edit it in Meta Ads Manager), no_change. A revert gives the ad its old creative back.
